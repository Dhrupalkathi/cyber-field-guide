# Delivery guidance for CINS mentors

## Teaching approach

- Explain concepts in simple language before introducing terminology.
- Demonstrate with diagrams and everyday examples.
- Make students predict what will happen before showing an answer.
- Use short practical exercises instead of long tool demonstrations.
- Ask students to explain their reasoning, not merely repeat definitions.
- Encourage pair work and peer explanation.
- Let beginners ask basic questions without embarrassment.
- Offer extension tasks to experienced students without making them mandatory for everyone.

## Suggested learning cycle for each module

1. **Explain:** introduce the core concept.
2. **Demonstrate:** show a small example.
3. **Practise together:** solve a guided exercise.
4. **Practise independently:** complete a small task without step-by-step instructions.
5. **Explain back:** student teaches the concept to a peer or mentor.
6. **Record evidence:** save a diagram, script, notes or troubleshooting record.

## Mentoring and AI guidance

- Mentors should ask students to explain their answers and code.
- AI may be used for explanations and debugging support, but students remain responsible for verifying the result.
- Never paste credentials, private keys, personal records, confidential club files or sensitive vulnerability data into public AI tools.
- Students should disclose significant AI assistance when required by the assignment rules.
- A student who cannot explain submitted work should be asked to revise it, not simply awarded credit because the output runs.

## Accessibility and equipment

- Stage 0 and Stage 1 should work on an ordinary laptop or desktop with a web browser.
- Do not require Kali Linux, a paid licence, a high-end GPU or a local virtualisation setup.
- Offer a browser-based option for Python where possible.
- If a student has limited hardware or internet access, mentors should provide downloadable notes, small sample files and offline exercises where practical.
- A student should not be excluded from the foundations because they cannot install a specialised lab.

# Resource maintenance and review

The curriculum should be reviewed at least once per academic year and whenever a platform changes a course, retires a path or changes access conditions.

For every resource, the CINS guide should record:

- Resource name and official URL.
- Topic/module it supports.
- Beginner/intermediate/advanced level.
- Whether the content is free, freemium or paid (verify at review time).
- Whether an account or special hardware is needed.
- Last link-check date.
- Last content-review date.
- Review status: Link checked, Content reviewed, Practice tested, Needs review or Archived.

A link being reachable does not mean the course has been completed or its teaching quality has been tested. Keep those review statuses separate.

# Final checklist before publishing these stages

- [ ] Stage 0 explains cybersecurity beyond hacking.
- [ ] Ethics, scope, permission and safe lab boundaries are explicit.
- [ ] Personal security habits are included without collecting sensitive student information.
- [ ] Students are introduced to domains without being forced to specialise.
- [ ] Stage 1 teaches computer fundamentals before detailed networking or operating-system administration.
- [ ] Python begins in Stage 1 and continues in later stages.
- [ ] No Kali Linux or expensive hardware is required.
- [ ] The TryHackMe Pre Security path is used selectively so it does not override the CINS sequence.
- [ ] Every module has learning outcomes, practice and a checkpoint.
- [ ] Students produce evidence of learning, not only certificates.
- [ ] Resources have review dates and maintenance labels.
