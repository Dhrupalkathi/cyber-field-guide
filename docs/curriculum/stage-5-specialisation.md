# Stage 5 — Specialisation and Advanced Study

**Level:** Developing practitioner to advanced learner  
**Audience:** Learners who have completed the shared CINS foundations and Stage 4 domain exploration  
**Prerequisites:** Stage 0 — Orientation, Stage 1 — Computer Fundamentals, Stage 2 — Technology Foundations, Stage 3 — Cybersecurity Core, and Stage 4 — Domain Exploration  
**Required operating system:** Depends on the selected pathway; no single operating system is required for the whole stage  
**Required specialist tools:** None for the conceptual curriculum; pathway-specific tools and labs are optional and must be selected deliberately  
**Primary scope:** Structured, deeper study in one or more cybersecurity domains, supported by evidence-based practice, mentoring, documentation, and a substantial learning project  
**Purpose:** Help learners develop demonstrable, responsible capability in a chosen area without implying that one course or project makes someone job-ready.

Stage 5 is where a learner moves from **understanding the cybersecurity landscape** to **developing depth in a selected area**. It is not one fixed sequence of tools, certifications, or exploit exercises. Learners choose a primary pathway, strengthen its prerequisites, study authoritative material, practise in a controlled environment, and produce work that can be reviewed.

> **Specialisation is a direction, not a permanent label.** You may begin with one pathway and later combine it with another. Real security roles often cross domain boundaries.

## How Stage 5 fits into the CINS curriculum

| Stage | Role in the learning journey |
|---|---|
| Stage 0 — Orientation and Cybersecurity Awareness | Understands the field, ethical responsibilities, authorisation, and safe learning. |
| Stage 1 — Computer Fundamentals | Builds the computing and programming foundations. |
| Stage 2 — Technology Foundations | Builds networking, Linux, Windows, and Internet/Web knowledge. |
| Stage 3 — Cybersecurity Core | Establishes shared security reasoning, risk, controls, identity, cryptography, monitoring, response, and governance. |
| Stage 4 — Domain Exploration | Compares professional domains, workflows, evidence, prerequisites, and boundaries. |
| **Stage 5 — Specialisation and Advanced Study** | Develops depth in a selected pathway through progressive study, supervised practice, and reviewed projects. |

Stage 5 assumes the learner can explain the foundations rather than merely recognise the terms. If a pathway exposes a gap in networking, operating systems, programming, web fundamentals, or security principles, return to the relevant earlier module before adding more tools.

## How to choose a pathway

Choose based on the work you want to understand and practise, not only on job titles, social-media trends, tool popularity, or salary claims.

| If you are most interested in… | Start with this pathway |
|---|---|
| Assessing systems within a written scope and explaining weaknesses | A — Security Assessment and Penetration Testing |
| Understanding how software and APIs can be built and verified securely | B — Application and API Security |
| Monitoring environments, investigating alerts, and improving detections | C — Blue Team, SOC, and Detection Engineering |
| Reconstructing incidents and analysing digital evidence or malicious software | D — DFIR and Malware Analysis |
| Researching adversary activity and producing evidence-backed intelligence | E — Threat Intelligence and OSINT |
| Securing networks, cloud services, containers, and infrastructure | F — Network, Cloud, and Platform Security |
| Building reusable safeguards into systems, delivery pipelines, and identity services | G — Security Engineering, DevSecOps, and IAM |
| Managing organisational risk, assurance, audit, and privacy | H — Governance, Risk, Compliance, and Privacy |
| Securing connected devices and systems that interact with the physical world | I — Mobile, IoT, and OT Security |

You do not need to choose forever. A learner interested in application security may later combine it with security engineering; a blue-team learner may add threat intelligence or DFIR. Begin with one primary pathway so that learning has a clear direction.

## Entry readiness

Before beginning a specialist pathway, check that you can:

- Explain the purpose and limits of the domain you selected, using the Stage 4 material.
- Identify the technical foundations the pathway expects and honestly mark any gaps.
- Explain authorisation, scope, privacy, evidence handling, and safe-learning boundaries.
- Read official documentation, distinguish facts from assumptions, and record sources.
- Use basic programming or scripting concepts where the pathway requires them.
- Ask for review when an activity could affect another person, service, device, account, or physical process.

A learner may begin reading a pathway before every prerequisite is complete. However, do not skip a prerequisite that is necessary to perform a practical activity safely or understand its results.

## Part I — Shared specialist practice

These modules apply to every pathway. They are not a second copy of Stage 3: they focus on how to plan, perform, explain, and review deeper specialist work.

### Module 5.1 — Build a specialisation plan

**Topics**

- Translate a domain of interest into a specific learning objective.
- Use tasks, knowledge, and skills to describe capability rather than relying only on job titles.
- Identify prerequisite knowledge, learning gaps, and a realistic order for closing them.
- Distinguish learning objectives, practice tasks, portfolio evidence, and professional requirements.
- Set a sustainable scope, time budget, and review point.
- Revisit the plan as interests and evidence change.

**Learning outcomes**

A learner can produce a short pathway plan with a clear objective, prerequisite checklist, study sequence, evidence of progress, and a review date.

### Module 5.2 — Research and technical evidence

**Topics**

- Find primary sources: standards, official documentation, vendor advisories, technical specifications, and original research.
- Evaluate source authority, date, version, scope, and assumptions.
- Separate direct observations, interpretations, hypotheses, and conclusions.
- Preserve references, timestamps, versions, and reproducible context where appropriate.
- Explain uncertainty, limitations, and alternative explanations.
- Avoid presenting an AI-generated explanation or an unverified online claim as evidence.

**Learning outcomes**

A learner can create a sourced technical note that makes its claims, evidence, assumptions, and limitations clear.

### Module 5.3 — Design a safe practice environment

**Topics**

- Select a lab that matches the learning objective and the learner's current level.
- Understand ownership, written authorisation, rules of engagement, data boundaries, and platform terms.
- Prefer synthetic datasets, intentionally vulnerable applications, isolated local environments, and approved training platforms.
- Understand isolation, snapshots, reset procedures, network exposure, and account separation at a conceptual level.
- Consider privacy, licensing, cloud charges, hardware limits, and data retention before setup.
- Stop when scope, safety, or permission is unclear.

**Learning outcomes**

A learner can explain why a proposed practice environment is appropriate, what it is allowed to do, what it must not touch, and how it will be reset or cleaned up.

### Module 5.4 — Specialist workflow and quality

**Topics**

- Turn a question or requirement into a bounded plan.
- Record assumptions, environment details, versions, and methodology.
- Use peer review, checklists, repeatable steps, and quality gates.
- Distinguish tool output from a validated result.
- Communicate severity and impact in context rather than exaggerating.
- Record false positives, failed hypotheses, and lessons learned.

**Learning outcomes**

A learner can describe and defend a repeatable workflow, including its quality checks and limitations.

### Module 5.5 — Professional reporting and communication

**Topics**

- Write for technical and non-technical readers.
- Structure a report around purpose, scope, method, evidence, impact, limitations, and recommendations.
- Use diagrams, timelines, tables, and concise evidence excerpts appropriately.
- Protect sensitive information and remove secrets from examples.
- Give actionable recommendations with ownership and verification criteria.
- Explain what is not known and what further evidence would be needed.

**Learning outcomes**

A learner can prepare a clear, audience-appropriate report that another person can review without relying on unsupported claims.

### Module 5.6 — Project, review, and continued development

**Topics**

- Define a project question that is narrow enough to complete and broad enough to demonstrate learning.
- Agree on scope, deliverables, safety controls, milestones, and review expectations.
- Maintain a project log and cite sources.
- Seek mentor or peer feedback at meaningful checkpoints.
- Revise the work in response to evidence and review.
- Reflect on skills gained, gaps remaining, and the next learning objective.

**Learning outcomes**

A learner can complete a bounded project, present the work and its evidence, respond to review, and identify the next step in their development.

## Part II — Specialisation pathways

Each pathway is a structured outline, not a claim that every listed topic must be mastered in one semester. The mentor and learner should select a sensible subset based on prior knowledge, available time, lab access, and the project's risk.

## Pathway A — Security Assessment and Penetration Testing

**Mission:** Assess an explicitly authorised system against a written scope, validate relevant weaknesses, explain their impact, and help the owner reduce risk.

**Recommended foundations:** Networking, Linux and Windows concepts, web fundamentals, scripting, security principles, and the Stage 4 assessment module.

**Progressive topics**

1. Assessment planning: objectives, asset inventory, scope, exclusions, test windows, contacts, and rules of engagement.
2. Methodology: threat-informed planning, attack-surface understanding, test coverage, and evidence quality.
3. Vulnerability analysis: distinguish exposure, weakness, exploitability, impact, and risk.
4. Controlled validation: understand the purpose and limitations of verification in a deliberately authorised lab.
5. Reporting: reproducible evidence, business impact, remediation guidance, and retest criteria.
6. Professional practice: responsible disclosure, client communication, data minimisation, and stopping conditions.

**Project direction:** Produce a scoped assessment plan and a report based on a purpose-built training application or a supplied synthetic assessment dataset. Do not test a public or third-party target without explicit written permission.

**Evidence of learning:** A clear scope, methodology, evidence log, prioritised findings, remediation guidance, and limitations.

## Pathway B — Application and API Security

**Mission:** Help software teams identify and reduce weaknesses in application design, implementation, and API behaviour.

**Recommended foundations:** Programming, HTTP, browser/server architecture, databases, authentication and authorisation, and basic software development.

**Progressive topics**

1. Secure application architecture, trust boundaries, data flows, and threat modelling.
2. Authentication, session management, authorisation, and object-level access control.
3. Input handling, output encoding, injection classes, file handling, and business-logic risks.
4. API design and verification: object and function authorisation, resource limits, inventory, and third-party API use.
5. Secure coding, code review, dependency and supply-chain risk, and secrets management.
6. Security verification using versioned standards and testing methodologies.
7. Communicating findings to developers and verifying fixes.

**Project direction:** Review a deliberately vulnerable training application or a small application you own. Map its trust boundaries, write security requirements, document a limited set of findings, and propose code-level or design-level fixes.

**Evidence of learning:** Threat model, security requirements, test rationale, validated findings, and a remediation or verification note.

**Further reading:** [OWASP Web Security Testing Guide](https://owasp.org/www-project-web-security-testing-guide/), [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/), and [OWASP API Security](https://owasp.org/www-project-api-security/).

## Pathway C — Blue Team, SOC, and Detection Engineering

**Mission:** Improve an organisation's ability to observe its environment, investigate suspicious activity, detect relevant behaviours, and respond proportionately.

**Recommended foundations:** Networking, Windows and Linux event concepts, identity, logs, security principles, and basic scripting or data handling.

**Progressive topics**

1. Telemetry design: endpoint, identity, network, application, and cloud event sources.
2. Log structure, timestamps, parsing, normalisation, retention, and data quality.
3. Alert triage: context, corroboration, prioritisation, escalation, and closure.
4. Detection engineering: translate a threat hypothesis into a documented and testable detection.
5. Threat hunting: develop questions, identify data requirements, examine evidence, and record uncertainty.
6. Detection validation: coverage, false positives, false negatives, test data, and tuning.
7. Incident coordination, playbooks, handovers, and operational improvement.

**Project direction:** Use a supplied synthetic log dataset to investigate a fictional alert, document the timeline and competing explanations, and propose a detection with test cases.

**Evidence of learning:** Investigation notes, event timeline, detection rationale, test cases, and an improvement proposal.

## Pathway D — Digital Forensics, Incident Response, and Malware Analysis

**Mission:** Help establish what happened during a security event, preserve and analyse authorised evidence, and support safe response and recovery.

**Recommended foundations:** Operating systems, filesystems, networking, scripting, security principles, and careful technical documentation.

**Progressive topics**

1. Incident response planning, roles, escalation, containment decisions, and recovery coordination.
2. Evidence sources and acquisition concepts: files, logs, memory, disk images, network records, and cloud audit data.
3. Evidence integrity, chain of custody, timestamps, time zones, and documented handling.
4. Timeline construction, hypothesis testing, alternative explanations, and reporting limitations.
5. Malware concepts: file formats, static properties, behavioural indicators, and defensive interpretation.
6. Safe malware-analysis principles, isolation, legal authority, and why unknown samples must not be run on everyday devices.
7. Incident lessons, recovery, evidence retention, and post-incident improvement.

**Project direction:** Analyse a fictional incident using synthetic logs and a prepared evidence manifest. Build a timeline, distinguish observations from interpretations, and write a response summary. Malware study must use curated, non-executable examples or an approved isolated training environment under supervision.

**Evidence of learning:** Evidence register, integrity notes, timeline, analysis report, and response recommendations.

**Further reading:** [NIST SP 800-61 Rev. 3](https://csrc.nist.gov/pubs/sp/800/61/r3/final) and [NIST SP 800-86](https://csrc.nist.gov/pubs/sp/800/86/final). Consult current organisational and legal requirements; these references are not legal advice.

## Pathway E — Threat Intelligence and OSINT

**Mission:** Answer defined questions about threats or events using lawfully obtained information, transparent sourcing, and an explicit assessment of confidence.

**Recommended foundations:** Networking and web fundamentals, research skills, source evaluation, writing, privacy, and basic data handling.

**Progressive topics**

1. Intelligence requirements, stakeholders, priority questions, and the intelligence cycle.
2. Source evaluation, provenance, reliability, corroboration, and information gaps.
3. Threat landscape research and interpretation of public technical reporting.
4. Indicators, infrastructure, adversary behaviours, and the limits of attribution.
5. Structured analysis: competing hypotheses, confidence, assumptions, and analytic bias.
6. OSINT ethics, privacy, minimisation, platform terms, and protection against doxxing or harassment.
7. Intelligence products: briefings, assessments, source notes, and actionable recommendations.

**Project direction:** Prepare a sourced threat-landscape briefing for a fictional organisation using public reports and synthetic indicators. State confidence and avoid identifying or profiling private individuals.

**Evidence of learning:** Intelligence requirement, source register, analytic notes, confidence statements, and a concise briefing.

## Pathway F — Network, Cloud, and Platform Security

**Mission:** Design, assess, and improve the security of networks, hosted infrastructure, cloud services, containers, and platform configurations.

**Recommended foundations:** Networking, Linux and Windows, DNS and web fundamentals, identity, virtualisation concepts, and basic scripting.

**Progressive topics**

1. Network architecture, segmentation, trust zones, remote access, and secure management.
2. Network security controls, monitoring, configuration review, and resilience.
3. Cloud shared-responsibility models, account and subscription structure, identity, and governance.
4. Cloud network design, storage permissions, logging, key management, and workload protection.
5. Container fundamentals, image provenance, runtime boundaries, orchestration concepts, and secrets.
6. Infrastructure as code, configuration baselines, policy, and change review.
7. Cost, availability, backup, recovery, and secure operational handover.

**Project direction:** Design a secure reference architecture for a fictional small organisation. Include a network diagram, identity model, logging plan, backup and recovery assumptions, and a review of likely misconfigurations using a supplied configuration example.

**Evidence of learning:** Architecture diagram, control rationale, configuration review, risk register, and operational checklist.

## Pathway G — Security Engineering, DevSecOps, and IAM

**Mission:** Build security into systems, development workflows, identity services, and operational processes so that safeguards are repeatable and maintainable.

**Recommended foundations:** Programming, software development lifecycle, operating systems, networking, authentication, authorisation, and security principles.

**Progressive topics**

1. Security requirements, architecture patterns, threat modelling, and design review.
2. Secure coding principles, code review, dependency management, and secrets handling.
3. CI/CD security concepts, build provenance, pipeline permissions, and protected release processes.
4. Security automation: quality gates, policy checks, exception handling, and test design.
5. Identity lifecycle, federation, MFA, role-based and attribute-based access, and privileged access.
6. Service identities, workload identity, secrets rotation, access reviews, and least privilege.
7. Observability, maintainability, control effectiveness, and developer experience.

**Project direction:** Design a secure delivery workflow or identity lifecycle for a fictional software team. Explain trust boundaries, permissions, control checks, exception handling, and how the team will verify that safeguards work.

**Evidence of learning:** Architecture or workflow diagram, security requirements, policy examples, test plan, and review record.

## Pathway H — Governance, Risk, Compliance, Audit, and Privacy

**Mission:** Help organisations understand obligations, make informed risk decisions, design and assess controls, protect personal information, and provide credible assurance.

**Recommended foundations:** Stage 3 security principles, analytical writing, organisational processes, data protection concepts, and basic system architecture.

**Progressive topics**

1. Governance structures, accountability, policy hierarchy, and risk ownership.
2. Risk assessment, treatment, acceptance, monitoring, and communication.
3. Control objectives, design, implementation, evidence, and effectiveness testing.
4. Framework selection and mapping without confusing guidance with law or certification.
5. Audit planning, sampling, evidence quality, findings, and corrective actions.
6. Privacy principles: purpose, minimisation, access, retention, disclosure, and rights.
7. Supplier assurance, third-party risk, contracts, and continuous improvement.

**Project direction:** Create a fictional organisation's risk register and control-mapping pack for a proposed student-record service. Include data flows, privacy questions, evidence requests, and clearly stated assumptions.

**Evidence of learning:** Risk register, control matrix, privacy review, evidence plan, and management summary.

## Pathway I — Mobile, IoT, and Operational Technology Security

**Mission:** Apply security principles to mobile devices, connected products, embedded systems, and operational environments while respecting hardware, lifecycle, safety, and availability constraints.

**Recommended foundations:** Networking, operating systems, hardware concepts, identity, secure development, and safety-aware risk assessment.

**Progressive topics**

1. Mobile platforms, application permissions, secure storage, device management, and update lifecycle.
2. Mobile application architecture, data handling, platform security controls, and verification concepts.
3. Embedded and IoT device lifecycle: identity, secure boot, firmware updates, vendor support, and physical exposure.
4. Device communication, segmentation, management interfaces, and telemetry.
5. OT concepts: industrial control systems, sensors, actuators, process availability, and safety constraints.
6. Remote access, change management, asset visibility, vendor coordination, and incident planning.
7. Specialist assurance, safety cases, and why live testing requires explicit coordination and competent supervision.

**Project direction:** Produce a security and lifecycle review for a fictional connected-device deployment. Do not test real campus devices, industrial equipment, medical devices, or other live physical systems.

**Evidence of learning:** Asset and data-flow map, threat model, lifecycle review, safety constraints, and prioritised recommendations.

## Part III — Specialist project and portfolio

A Stage 5 project should demonstrate reasoning and communication, not merely the number of tools used or the number of vulnerabilities found.

A suitable project should include:

1. **Question and purpose:** What are you trying to understand, design, verify, or improve?
2. **Scope and permission:** Which systems, data, people, and activities are included or excluded?
3. **Prerequisites:** What knowledge and supervision are needed?
4. **Method:** What sources, sample data, tools, and procedures will you use, and why?
5. **Evidence:** What observations support the result? What is uncertain?
6. **Outcome:** What did you learn, design, validate, or recommend?
7. **Limitations:** What did you not test or establish?
8. **Review:** What feedback did you receive, and what changed as a result?
9. **Reflection:** Which skills improved, and what should be learned next?

A portfolio may contain original notes, diagrams, threat models, synthetic-data investigations, code written by the learner, architecture reviews, reports, and project reflections. Remove credentials, private information, client material, personal data, and sensitive technical details before sharing. Obtain permission before publishing any work involving another organisation.

## Safe practice and professional boundaries

- Only assess systems, accounts, applications, devices, and data that you own or are explicitly authorised to use.
- Written scope and rules of engagement take precedence over assumptions or tool capabilities.
- Use intentionally designed training environments, synthetic data, and approved labs for practical work.
- Do not run unknown malware on everyday devices or expose a lab to networks without understanding the risk.
- Do not perform denial-of-service, destructive testing, persistence, evasion, credential theft, or social engineering unless a specific controlled programme explicitly authorises a narrowly defined activity and suitable supervision is in place.
- Do not collect, publish, or infer private information about real people for curiosity or entertainment.
- Do not test live production, medical, industrial, campus, or safety-critical systems without formal authorisation and specialist oversight.
- Understand cloud permissions, data exposure, and possible charges before creating resources.
- Protect evidence and secrets; share only what is necessary with authorised people.
- Stop and ask a mentor or system owner if an activity exceeds your knowledge, authority, or agreed scope.

The curriculum does not require exploitation of real targets, malware execution, paid cloud accounts, expensive hardware, or a particular commercial tool. A learner can demonstrate substantial understanding through analysis, design, synthetic datasets, documentation, and reviewed projects.

## AI-guided specialist learning

Use an AI assistant as a tutor and reviewer, not as an authority or an operator that you follow blindly. Ask it to explain prerequisites, compare approaches, review a fictional design, generate synthetic examples, or challenge your assumptions.

You can use this prompt:

> I am following CINS Stage 5 and have selected **[pathway]**. My current level is **[describe what I already understand]**. Help me create a progressive learning plan for **[specific topic or project]**. Identify prerequisites and explain unfamiliar terms before using them. Use fictional systems and synthetic data. Recommend primary sources and official documentation, and distinguish standards, guidance, and examples. Give me a way to verify my understanding and explain common mistakes. Do not assume I have paid tools, specialist hardware, or permission to test real systems. Do not provide instructions that exceed the safe scope of my learning environment. State uncertainty and ask me to verify important technical claims.

Verify important claims against primary sources and current documentation. Never paste credentials, private keys, personal records, confidential logs, unpublished vulnerabilities, or another organisation's evidence into a public AI service.

## Stage 5 exit outcomes

A learner who completes a meaningful Stage 5 pathway should be able to:

- Explain the mission, scope, and professional responsibilities of their selected domain.
- Demonstrate deeper knowledge of the pathway's core concepts and prerequisites.
- Select an appropriate method or workflow and explain why it fits the question.
- Work within explicit authorisation, privacy, safety, and evidence-handling boundaries.
- Produce a reviewed artefact that demonstrates their reasoning, such as a report, design, investigation, detection, risk assessment, or code contribution.
- Explain limitations and uncertainty without overstating results.
- Incorporate feedback and identify further development needs.
- Describe the next realistic learning step, including where mentorship or formal training is needed.

**Completing Stage 5 material does not guarantee employment, professional certification, or job readiness.** Capability depends on the depth and quality of practice, feedback, experience, and the requirements of the role or organisation.

## Authoritative references and frameworks

Use these as starting points and check the current version before relying on them. They are reference material, not a requirement to read every document.

- [NIST NICE Framework Resource Center](https://www.nist.gov/itl/applied-cybersecurity/nice/nice-framework-resource-center) — describes cybersecurity work through tasks, knowledge, skills, work roles, and competency areas.
- [NIST Cybersecurity Framework 2.0](https://www.nist.gov/cyberframework) — a risk-management framework useful across technical and governance pathways.
- [MITRE ATT&CK](https://attack.mitre.org/) — a knowledge base of adversary tactics and techniques based on observed behaviour; it is not a complete security methodology or a checklist.
- [OWASP Web Security Testing Guide](https://owasp.org/www-project-web-security-testing-guide/) — a methodology reference for authorised web application testing.
- [OWASP Application Security Verification Standard](https://owasp.org/www-project-application-security-verification-standard/) — requirements for verifying application security controls.
- [OWASP API Security Project](https://owasp.org/www-project-api-security/) — API security risks and guidance.
- [NIST SP 800-61 Rev. 3](https://csrc.nist.gov/pubs/sp/800/61/r3/final) — incident-response recommendations integrated with cybersecurity risk management.
- [NIST SP 800-86](https://csrc.nist.gov/pubs/sp/800/86/final) — guidance on integrating forensic techniques into incident response; consult applicable legal and organisational requirements.
- [CIS Critical Security Controls](https://www.cisecurity.org/controls) — prioritised safeguards that can inform defensive and engineering work.

## What comes after Stage 5?

Specialisation is continuous. After completing a pathway project, learners can deepen the same domain, add a complementary pathway, contribute reviewed material to the CINS guide, seek mentorship, or pursue internships and formal training whose prerequisites they meet. Revisit the [Curriculum overview](index.md) for the overall learning sequence and use the resource library for optional references.
